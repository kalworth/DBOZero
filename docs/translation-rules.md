# 翻译与构建规则

本文档是维护 `data/` 翻译表和构建补丁时必须遵守的规则。
日常翻译流程见根目录 `README.md`，模块结构见 `docs/development.md`。

## 翻译表规则

- TSV 文件保持制表符分隔，不要用空格对齐列。
- `data/new_translations.tsv`：日常新增词条队列，只填 `填写中文` 列；ID、原文、参考列保持原样。
- `data/translations.tsv`：已接受译文主表，修改现有译文时只改 `zh_cn` 列。
- TBL 行的 `位置=*` 表示按原文做 UTF-16LE 通配替换，不要改成猜测的偏移。
- 候选/发现文件（`reports/internal/`）不代表字符串在游戏里可见。是否翻译以用户选择、截图或明确的文本相关性为准。
- `tbl0.pak` 的 `AzureRenegade`、`BurningRenegade` 是内部称号特效令牌，必须逐字节保持原文；`tbl1.pak` 里带空格的显示名可以翻译。

## 文本来源优先级

- 短普通 UI 标签、属性名、状态标签等非富文本，默认以 `local_data.dat` / `local_sync_data.dat` 为准。
- 富文本、长文本、弹窗消息、系统消息，以及已知运行时来源是 `lang0`/`tbl` 的新 UI/TBL 文本，用 `lang0.pak` 或 TBL。
- 不要让旧的 `local_data.dat` 措辞覆盖新元素术语。水/火/冰/雷/风等新属性内容保持当前 `lang0`/新内容译法，除非有运行时证据表明用了别的来源。
- 如果某个可见短标签确实来自 `lang0.pak`（即使 `local_data.dat` 里也有同 key），先通过截图或输出字节验证运行时来源，再加窄范围的 `lang0` 特例。
- 已验证的 `lang0.pak` 拥挤状态标签模式是定长无引号替换：把整个带引号字段（如 `"STR"`）替换为等长值（如 GBK 下的 `力量 `）。仅当输出文件大小不变且游戏实测接受时才允许。
- 不要把无引号 `lang0` 模式当成通用策略；目前只限于已验证的六个基础状态属性等短标签，新案例需单独测试。

## 编码与打包规则

- `local_data.dat`、`local_sync_data.dat` 生成为 ANSI 游戏文件，不是 UTF-8。
- 面向游戏的生成文件绝不能转换成 UTF-8 中文文本。
- `lang0.pak` 使用固定原始字节补丁，是唯一有原始字段长度硬限制的面。译文 GBK/CP950 转换后超长就必须缩短。
- `lang0.pak` 的长度规则不适用于 Taiwan/RDF 或 TBL。
- TBL 字符串是定长二进制字段。存储长度前缀保持不变；较短的 UTF-16LE 替换串用 NUL 字节（`00 00`）补齐，绝不用可见空格（`20 00`）。
- 不要为了让 TBL 名称匹配旧文本长度而手动缩短，除非补丁器报告了真正不安全的行。

## 源快照刷新规则

`src_file/DBOZero` 被更新为新版游戏快照时：

0. 前提：游戏目录必须是**官方原版文件**。如果先打了补丁再刷新，`dboc refresh`/`update` 会检测到游戏文件与构建输出逐字节一致并拒绝同步；此时用启动器文件校验/修复恢复原版后再运行。安全顺序：游戏更新 → 先刷新/更新 → 再把补丁覆盖进游戏。
1. 运行 `dboc update`；它会自动建立本地 Git 恢复点，并包含已跟踪的 `data/new_translations.tsv` 变更。
2. 手动分步执行时，先建恢复点再 `dboc scan`。
3. 手动翻译完成后运行 `dboc build`。
4. 检查构建统计，重点是 `pack/lang0.pak`、`pack/tbl0.pak`、`pack/tbl1.pak` 的 `missing` 计数。
5. 如果固定 TBL 行发生移动，优先用当前 v3 数据；只有明确需要恢复旧 override 时才用 legacy 重定位脚本。
